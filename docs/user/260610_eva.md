# 2026-06-10 项目完整性与体验评估

## 1. 评估范围与前提

- [事实] 评估对象：线上内网地址 `http://172.25.10.143:5174/`，以及当前仓库源码与项目文档。
- [事实] 用户侧页面为内网公开项目，不需要登录流程；这一点符合项目定位，不作为缺陷。
- [事实] 管理入口为 `/admin`，当前密码为 `admin`；admin 需要单独评估功能可用性与写入安全边界。
- [事实] 已检查入口：`/`、`/ble`、`/bt`、`/earbuds`、`/wifi`、`/admin` 均可返回 SPA 页面；`/manifest.json` 与 `/assets/FontManifest.json` 可正常返回 JSON；`/api/chips` 可返回芯片 JSON 文件集合。
- [推断] 主要使用者是内部工程、FAE、产品/销售支持人员；桌面端是主战场，移动端应至少做到可浏览和不破版。

## 3. 用户侧评估

### 3.1 完整性

优点：

- BLE、BT Classic、Wi-Fi、TWS Earbuds 四类入口已经覆盖项目定义的核心场景。
- BLE/BT/Wi-Fi 页面具备“参数配置 -> KPI -> 电流时间线图”的仿真闭环。
- Earbuds 页面具备芯片搜索、过滤、多芯片选择、场景/Tx/Rx/CPU 多维数据对比，适合横向选型。
- 深链参数可表达 tab、view、chips、focus 等状态，便于内部分享具体对比视图。
- 用户侧无登录流程，符合“内网公开工具”的使用效率要求。

主要缺口：

- 缺少面向汇报和复盘的导出能力，例如 CSV、PNG、PDF 或一页式报告导出。
- 缺少公式口径/数据来源的轻量说明入口；对非开发用户来说，平均电流、平均功耗、续航估算的可信度解释不足。
- 缺少“预设场景/模板”管理，例如常用 BLE 广播、典型 TWS 音频、典型 Wi-Fi sniff 等一键配置。
- 多页面交互已经丰富，但跨页面的结果对照和收藏能力还弱。

### 3.2 交互性

优点：

- 参数表单、滑块、开关、芯片选择、排序、搜索、hover 图表等基础交互齐全。
- 当前桌面布局能同时看到配置、KPI 和图表，适合反复调参。
- Earbuds 对比表格的热力颜色、best/avg/worst 概念有助于快速定位优劣。
- “Hide sleep/gaps”等开关降低了低功耗长间隔场景下的图表阅读负担。

主要缺口：

- 图表主要依赖 hover，触屏设备、键盘用户和截图场景下的信息可访问性不足。
- 图表缺少缩放、框选、导出、固定 tooltip 等高级分析交互。
- 移动端窄屏下左侧导航和配置面板占用过多横向空间，主内容区域被挤出首屏，影响可用性。
- 表格与图表对颜色依赖较强，建议补充数值标签、文本摘要或可切换的色盲友好方案。

### 3.3 UI 界面

优点：

- 整体采用 Material 3 风格，卡片、图标、间距、边框和主题色较统一。
- 桌面端信息密度适中，左侧导航 + 配置面板 + 主工作区的结构清楚。
- Earbuds 对比页有明确的“芯片筛选/列表/指标表格”工作流，偏工具型而非营销型页面，方向正确。
- admin 登录页视觉完成度较高，和主应用风格一致。

主要缺口：

- 移动端布局需要专门设计：当前窄屏更像桌面布局硬压缩，建议改为抽屉/顶部导航 + 配置折叠 + 结果优先。
- 英文界面中仍出现中文单位，例如电池寿命显示 `天`；图表轴标题还有硬编码 `Current (mA)` / `Time (ms)`，i18n 未完全收口。
- 部分历史页面或备用代码仍有中文硬编码，例如 `BT 模式`，容易在后续路由或重构中回流。
- 图表轴标签、KPI 卡片和表格列头在极窄宽度下需要更强的换行/压缩策略。

## 4. Admin 界面评估

### 4.1 功能完整性

优点：

- `/admin` 与用户侧分离，不影响公开用户流程。
- 登录后主结构包含 6 个一级 tab：BLE CASE、BT CASE、Earbuds、Wi-Fi、Ops、Heat。
- Earbuds 下还有 Scene、Tx、Rx、CPU Consumption 子 tab，结构符合当前数据拆分。
- 通用 JSON 编辑器支持搜索、选择、添加、复制、删除、排序、上移/下移、重置种子、保存、全量导出等维护动作。
- Earbuds 数据支持 Excel 同步 NoisePink 详情，能降低手工录入成本。
- 后端写入前会生成 `.chip_backups/<时间戳>/` 备份，这是数据落地链路中的重要保护。
- admin 数据仓储 lazy load，普通用户首次进入主页面不再等待 admin-only 数据加载，这对首屏性能有正面作用。

主要缺口：

- JSON 编辑器能力很强，但对非开发维护者偏“原始数据编辑器”；复杂嵌套字段建议逐步做成领域化表单。
- 保存是高影响操作，需要更明确的变更 diff、未保存状态、危险字段提示和备份恢复入口。
- Ops、Heat 当前更像占位说明，若短期无计划，建议在 UI 上明确“暂未开放/规划中”，避免误判为功能缺失。
- admin 也是桌面优先，移动端维护体验预计较弱；这可以接受，但应明确不把移动维护作为目标。

### 4.2 Admin 安全边界

这是当前最需要优先处理的点。

[事实] 当前 `lib/main.dart` 中 `adminSecretKey` 为常量 `admin`，登录校验在前端完成；`AdminSessionStore` 使用 `shared_preferences` 保存本地 unlocked 状态。  
[事实] `tool/chip_server/bin/server.dart` 暴露 `GET /api/chips` 和 `POST /api/chips`，其中 POST 会写回 `assets/data/chips/**.json`；CORS 当前为 `Access-Control-Allow-Origin: *`。  
[结论] 这意味着 admin 密码主要是 UI 门禁，不是服务端写入权限控制。只要内网用户能访问后端 API，就可能绕过 `/admin` 页面直接调用 POST。

建议：

- P0：给 `/api/chips` 的 POST 增加服务端鉴权，至少使用部署环境变量配置 token，并要求前端保存/提交 token。
- P0：如果短期不做服务端鉴权，至少在 Nginx 或网关层限制 POST 来源，例如 IP allowlist、Basic Auth、VPN 分组或只在维护窗口开放。
- P0：生产/内网公开部署建议默认只开放 `GET /api/chips`，把写入 API 放到单独端口或内网更小范围。
- P1：收紧 CORS，不要对写入 API 使用 `*`。
- P1：把默认密码从源码常量移出，改为构建参数或部署环境变量；默认值不应是 `admin`。
- P1：增加操作审计日志，记录时间、操作者标识、写入文件数量和备份目录。

## 5. 部署与性能观察

优点：

- 线上深链和 SPA fallback 基本正常。
- `manifest.json`、字体清单等关键静态资源返回正常，前期 Web 部署修复已生效。
- `/api/chips` 能返回完整文件集合，说明当前线上数据后端已接入。
- CanvasKit 与字体本地化方向正确，适合内网部署，避免外部 CDN 依赖。

风险与改进：

- 资源大小写存在 fallback：index 中可能出现 `1306P`，磁盘文件为 `1306p.json`；当前 loader 会依次尝试原始、小写、大写，功能上可兜底，但线上会产生多次 404 日志和额外请求。建议统一 index 与文件名大小写，减少噪音和排查成本。
- admin 数据 API 与静态 Web 同源部署简单，但也放大了写入 API 的暴露面；建议读写分离或网关限制。
- 建议补一组固定的线上 smoke test：入口 200、静态 JSON MIME、CanvasKit WASM MIME、`/api/chips` 文件数量、核心芯片详情是否可加载。

## 6. 可维护性与文档

优点：

- 项目分层总体清楚，`models -> config -> services -> state -> widgets -> pages` 的方向基本可辨。
- task-log 对近期改动记录很细，尤其 admin 后端、Web 性能和 Earbuds 数据模型演进有迹可循。
- 数据拆分为多 JSON 文件后，长期维护比单大文件更清晰。

主要缺口：

- `lib/pages/admin_page.dart` 体量过大，后续建议拆成 login、top bar、tab shell、record list、field editor、domain-specific editor 等组件。
- `power_calculator.dart` 等服务层仍携带 `Colors.*` 这类展示层概念，算法和 UI 表达耦合偏高。
- `docs/ai/product-context.md`、`docs/ai/tech-context.md` 的部分描述已滞后，例如早期“无 HTTP/无持久化/无后端”的说法与当前 `shared_preferences`、`http`、`tool/chip_server` 不完全一致。
- `main_all_in_one.txt` 等历史整合文件容易误导搜索结果，建议标记归档或移出常规源码搜索范围。

## 7. 优先级建议

### P0：公开内网前必须处理

1. 保护 admin 写入 API：服务端鉴权、网关限制、POST 只对维护者开放。
2. 修复移动端主布局：小屏下改为配置折叠/抽屉，确保 KPI 和图表可直接访问。
3. 统一芯片资源文件名大小写：减少线上 404 fallback 噪音。
4. 清理明显 i18n 漏洞：电池寿命单位、图表轴标题、遗留中文硬编码。

### P1：提升可用性与可信度

1. 增加导出能力：CSV、PNG、PDF 或“一页报告”。
2. 增加图表缩放、固定 tooltip、键盘/触屏友好交互。
3. 为公式、数据来源、单位和估算假设提供轻量说明。
4. admin 增加 diff 预览、未保存提示、备份恢复入口。
5. 拆分 admin 大文件，降低后续维护风险。
6. 同步更新产品/技术文档，避免文档和实际架构继续分叉。

### P2：增强长期产品感

1. 常用场景模板与收藏/分享。
2. 多场景对比报告，例如同一芯片在 BLE/BT/Wi-Fi/TWS 下的组合续航。
3. 色盲友好主题和无障碍文本摘要。
4. 线上性能指标采集与烟测脚本。
5. admin 操作审计与版本历史。

## 8. 建议验收清单

用户侧：

- 窄屏 390px 下可以完成场景切换、参数调整、查看 KPI 和图表。
- 英文模式不出现中文单位或中文按钮。
- 任一核心页面可导出当前结果，至少支持 CSV 或 PNG。
- Earbuds 深链中的芯片 id 无效时，有明确提示或自动清理。
- 图表 hover 信息有等价的文本或表格入口。

Admin：

- 未授权请求不能 POST `/api/chips`。
- 写入 API 有服务端鉴权，不依赖前端常量密码。
- 保存前能看到变更摘要；保存后能看到备份位置或恢复入口。
- 重置、删除、批量写入等高风险操作有二次确认和明确影响范围。
- admin 默认密码不在源码中硬编码，部署时由环境配置。

部署：

- `/manifest.json`、`/assets/FontManifest.json`、CanvasKit WASM、`/api/chips` 都有自动 smoke test。
- 线上控制台没有批量资源 404 警告。
- 静态资源 MIME、缓存、gzip 策略稳定。

## 9. 结语

这个项目的核心价值已经很明确：它不是普通展示页，而是一个面向芯片功耗讨论的内部工作台。桌面端工具感、数据对比和 admin 数据落地已经搭起来了；下一步最值得投入的是把“可演示”推进到“可放心公开使用”：先收紧 admin 写入边界，再补移动响应、导出和 i18n 收尾。
